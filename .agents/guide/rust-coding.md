# rustを使用した開発におけるガイド

下記のガイドを守るにあたって，必要に応じて一次情報を確認する．

- クレートのバージョンや API は変化しうるため，必要な場合は公式ドキュメント・docs.rs・リポジトリ等の一次情報を確認すること
- 情報の更新が不要な一般的知識だけで完結する場合は，無理に外部検索しないこと

## エコシステム

標準ライブラリで学べる内容を優先し，外部クレートは目的に応じて選ぶこと．

## cargo

依存関係を追加・更新する前に，必要性と互換性を確認すること．

## トレンド

常に最新の書き方を考慮すること．ただし，可読性や効率性，保守性を考慮して最終的な記述方法を決定すること

## 命名規則

一般的な Rust 規則に従う（`snake_case` / `CamelCase` / `SCREAMING_SNAKE_CASE`）．

## 禁止事項

| 禁止                   | 理由                      | 例外                           |
| ---------------------- | ------------------------- | ------------------------------ |
| `unsafe`               | Rust 移行の意義がなくなる | 必要な場合は人間に確認         |
| 再利用困難なモジュール | 保守性低下                | トレイト・ジェネリクスで抽象化 |
| テストのない複雑なロジック | 品質担保に必須          | 学習用の最小スニペット         |
| `panic!`               | ユーザー体験が悪化        | どうしようもない場合のみ       |

## 言語使い分け

ユーザーの目に触れる文字列は英語で記述する．文字化けのリスクがあるため．

| 対象 | 言語 |
| --- | --- |
| `#[error(...)]` に渡すメッセージ文字列 | 英語 |
| `tracing::debug!/info!/warn!/error!` に渡すメッセージ文字列 | 英語 |
| rust-docs（`///`） | 日本語 |
| コメント（`//`） | 日本語 |

## エラーハンドリング

- `Result<T, E>` を基本とする
- `unwrap()` / `expect()` は最終コードで除去する
- エラー型は `thiserror` で定義することを推奨

## コードの変更粒度

- 一度に変更するファイルは少数にする
- 大規模リファクタは設計案と変更範囲を先に提案する

## フォーマット文字列

`println!` / `format!` 等のフォーマットマクロでは，識別子の種類に応じてスタイルを使い分ける．

| 対象 | スタイル | 例 |
| --- | --- | --- |
| シンプルな変数名・定数名 | `{variable}` 記法 | `"{e}"`, `"{SHADER_PATH}"` |
| 型パス・メソッド呼び出し等の式 | `"{}", expr` 記法 | `"{}", GpuContextError::AdapterNotFound` |

## コメント

- rust-docsを作成する
- 説明は日本語で行う
- `text-style`ガイドに従う
