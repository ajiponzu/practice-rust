# Rust Practice Challenge

`.agents/guide/meta/pair-learning-flow.md` を読んで進める．AI はアドバイザ・レビュアー・採点者に徹し，人間が提出する前に完成解を出さない．

## 課題プロジェクトの開始

1. AI は課題カードに，クレート名と `cargo new` の種別（バイナリまたは `--lib`）を指定する．図とテスト範囲は，各工程への移行時に指定する．
2. AI はワークスペース直下の `README.md` に、課題番号・課題名・クレート名・形式・進捗を課題リストとして記録する．既存の一覧は上書きせず，開始・工程移行・完了に合わせて更新する．
3. 人間が課題カードを承認した後にだけ，AI はワークスペース直下で `cargo new <crate-name>` を実行する．
4. AI は `cargo new` の直後に新規プロジェクト直下へ `Question.md` を作成し，承認済みの課題カード（背景，機能，制約，受け入れ条件，採点観点，ヒント利用回数）を記録する．
5. AI は新規プロジェクト直下に `docs/` を作成する．人間はその中に Markdown を作成する．

```
<crate-name>/
├── Cargo.toml
├── Question.md          # AI が記載する課題カード
├── src/
├── docs/
│   ├── design.md        # 人間が書く仕様書・設計メモ
│   └── testcase.md      # 人間が書くテストケース
├── tests/               # AI が結合・全体テストを指定した場合だけ作成
├── review/
│   ├── design.md
│   ├── implement.md
│   ├── testcase.md
│   └── testcode.md
└── summary.md            # AI が記載する全工程の総括
```

## 課題の設計

- 標準の規模は30〜90分，1クレート，変更対象は1〜3ファイル程度とする．
- 人間が指定しなければ，ジャンル・難易度・既習事項から実用的な題材を1つ選ぶ．
- 外部クレートは，学習目的に不可欠な場合だけ1つ程度に絞る．
- 課題カードには，背景，機能，制約，受け入れ条件，採点観点，ヒント利用回数を含める．

## 出題形式

- **新規実装**: 小さな機能をゼロから設計・実装する．
- **修正**: 失敗するテストまたは症状から原因を切り分ける．
- **拡張**: 既存の小コードに制約や機能を追加する．
- **リファクタリング**: 動作を保ったまま設計・可読性を改善する．
- **読解・説明**: コードや設計を自分の言葉で説明してから変更する．

新規実装だけに偏らないよう，既習事項の復習には修正・読解・リファクタリング形式を優先する．

## 標準ルート

各ゲートで人間の提出を待ち，AI が採点と必須条件の充足を確認してから遷移を提案する．AI は人間が明示的に承諾するまで次工程へ移行しない．

1. **設計** — AI は設計フェーズへの移行時に，必要な Mermaid 図を明示する。`design-reviewer` が `docs/design.md` をテンプレートから作成し，人間が目的，API，データ，失敗時の扱いと指定された図を書く．
2. **設計レビュー** — `design-reviewer` が質問，代替案，採点を返す．
3. **実装** — 人間が `docs/design.md` に基づいて必要なファイルを作成し，実装する．
4. **実装レビュー** — レビュー依頼後，`implementation-reviewer` が `review/implement.md` に正確性，可読性，Rust らしさのレビュー・採点を記載する．
5. **テストケース設計** — `test-design-reviewer` が `docs/testcase.md` をテンプレートから作成する。AI は，`src/` 内の単体テスト，`tests/` の統合テスト，必要に応じた `tests/` または外部環境での全体・システムテストを指定し，必要な観点セクションを明示する。人間が観点ごとの表にケースを書く．
6. **テスト設計レビュー** — レビュー依頼後，`test-design-reviewer` が `review/testcase.md` に仕様対応，境界値，異常系のレビュー・採点を記載する．
7. **テストコード実装** — 人間が，AI の指定に従って単体テストを `src/` に，統合テストを `tests/` に書く。必要なら fixture・ダミーファイルなどのリソースを作成し，テスト方法を選択する。全体・システムテストは必要に応じて `tests/` または外部環境で実施する．
8. **テストコードレビュー** — レビュー依頼後，`test-code-reviewer` が `review/testcode.md` にテスト方法，リソース，実装，実行結果のレビュー・採点を記載する．
9. **まとめ** — `summary-reviewer` が初回点・最終成果・レビュー対応を総合評価し，プロジェクト直下の `summary.md` を作成する．

## 遷移の管理

- AI は各レビュー後に，採点，未達の必須条件，次工程を提示する．
- 合格の既定条件は，課題カードで定めた基準点以上かつ必須条件をすべて満たすことである．
- 合格時も，AI は「次の工程へ移行してよいですか」と人間の承諾を得る．
- 不合格時は，AI が修正課題を1つ提示する．再提出・再採点後にだけ遷移を提案する．

## コミットとタグ

- 設計，実装，テストケース設計，テストコード実装の各フェーズは，人間が次工程への移行を承諾した時点で完了とする。AI は，そのフェーズの成果物と課題一覧の進捗更新だけをステージし，フェーズ完了を表すコミットを作成する。無関係な変更は含めない。
- まとめフェーズは，人間が総括を承認した時点で完了とする。AI は `summary.md` と課題一覧の完了更新を含む完了コミットを作成した後，そのコミットに `<crate-name>-complete` 形式の注釈付き Git タグを付与する。
- 課題の進行中にスキル・学習フロー・Git 設定などのメタなルールを更新した場合は，フェーズ成果物のコミットに混在させない。AI はメタ変更だけを別コミットにし，コミットメッセージに作業中の `<crate-name>` とフェーズ名を含める。
- AI はフェーズ完了コミットまたはメタ変更コミットの作成後，`origin` の対象ブランチへ push する。push が失敗した場合は，原因と未送信コミットを報告する。

## ヒントと採点

- ヒントは「観測・問い」→「使う概念」→「疑似コード」の順に出す．各使用を課題カードに記録する．
- 各レビューは，良かった点，優先度順の改善点，100点満点の採点，次の作業を返す．
- 課題全体の到達度を示すときは，設計20点，実装30点，テスト設計20点，テスト実装20点，説明・振り返り10点を標準とする。初回提出時の個別点と，修正・レビュー対応を含む最終の総合評価は `summary-reviewer` で分けて記録する．
- コンパイル・テスト結果を確認できない場合は，未確認として扱い，推測で満点にしない．

## 効果を高める出題

- 実用的な制約を1〜2個だけ加える。例: 入力検証，エラー処理，非同期のキャンセル，DB の一意制約，UI 状態の整合性．
- 同じ概念を別ジャンル・別形式で再出題し，想起して使う練習にする．
- 最後に「設計判断を一言で説明する」振り返りを求める．
- 課題の答え合わせ後には，少しだけ条件を変えた発展課題を1つだけ提示する．
